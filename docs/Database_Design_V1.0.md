2. Database Design Rules
PostgreSQL is the authoritative persistence layer for V1.
PostGIS must be enabled.
Tree/plantation locations must use PostGIS geometry rather than storing latitude and longitude as unrelated authoritative fields.
Use foreign keys and database constraints to protect relationships and identity.
Permanent Tree ID uniqueness must be enforced by the database.
Health records are historical/append-oriented; normal monitoring updates must not overwrite prior HealthLog events.
Verification is auditable through persisted reviewer, decision, timestamp, and reason data.
Passwords are stored only as secure hashes; plaintext passwords are never stored.
Private account information must not be copied into public tree-profile data or QR payload fields.
Exact API response formats are not defined by this document; the API Specification remains the API contract.
Do not add V2 AI/ML-specific tables merely because future features may need them.
Where a business rule is not frozen here, do not invent one; record it as an open decision.
3. Database Objectives
Represent users and their roles.
Represent plantation/tree records and verified Tree identity.
Persist spatial locations for map and geospatial queries.
Represent the manual verification workflow and audit trail.
Store deterministic species suitability rules.
Store health monitoring history.
Store rewards/activity records.
Support dashboard aggregation from trustworthy structured records.
Provide indexes and constraints needed for the semester pilot.

8. Tree Status Constraint
Pending → Under Review → Verified                         ↘ Rejected
New tree records must be Pending.
Only authorized application logic may transition status.
Verified is the prerequisite for permanent Tree ID issuance.
Rejected records retain their history.
Resubmission/re-review behavior is not frozen by this design.
9. Spatial Design — PostGIS
9.1 Required Extension
CREATE EXTENSION IF NOT EXISTS postgis;
The production/test database must verify PostGIS availability during setup/migrations.
Spatial queries must use PostGIS functions rather than application-side distance loops.
9.2 Geometry Column
location geometry(Point, 4326) NOT NULL
SRID 4326 is the recommended V1 storage reference for WGS84 latitude/longitude coordinates.
Frontend/API may use numeric latitude/longitude while the repository converts them into PostGIS geometry.
Database geometry must be treated as the authoritative stored location.
9.3 Spatial Index
CREATE INDEX idx_trees_location_gist ON trees USING GIST (location);
Use the GiST index for representative nearby/viewport spatial queries.
Do not retrieve all trees and calculate distances in JavaScript for normal map operations.

18. Tree ID Database Strategy
The exact textual format is a product/API decision already constrained by the PRD to be a unique stable identifier. The database design therefore specifies the integrity model rather than forcing an arbitrary format.
Verification = VERIFIED        ↓Tree Identity Service        ↓Generate candidate Tree ID        ↓Database UNIQUE constraint        ↓Persist Tree ID        ↓QR references Tree ID
Use a unique constraint/index on trees.tree_id.
Tree ID must be nullable before verification if the tree row is created before verification.
Tree ID should be generated within a controlled backend transaction/workflow to avoid duplicate issuance under concurrent verification.
Do not use a random frontend-generated string as the authoritative identity.
Exact format/prefix/sequence policy must be frozen in the API specification/project decision log before implementation.
19. Photo / Media Data Model
Tree and HealthLog records should store a photo reference/key/URL rather than large image binaries by default.
Actual media storage may be object storage or another approved storage implementation.
Storage provider is intentionally not frozen by this database document.
Media references must not contain private secrets.
Deletion/retention rules for media are not frozen and must be explicitly decided before destructive operations are implemented.
20. Dashboard Data Strategy
Dashboard metrics should be derived from transactional tables rather than manually maintained counters where practical.
Verified plantation count derives from trees with Verified status.
Verification metrics derive from registration and verification timestamps/events.
Health activity derives from health_logs.
Rewards derive from rewards.
Observed survival status must be based only on valid final health checks and must not infer death from missing logs.
Materialized views/caches are not required for V1 unless performance testing demonstrates a need.
21. Auditability
Registration creation timestamp supports VRR calculation.
Verification records preserve reviewer, decision, timestamp, and reason.
Health logs preserve submitting user and monitoring timestamp.
Reward events preserve activity and timestamp.
Do not hard-delete historical verification or health events as part of normal workflow operations.

23. Transaction Boundaries
User registration should be atomic with account creation.
Plantation registration should atomically create the tree record and required relational references.
Verification decision and its audit record should be committed atomically.
Verified Tree ID issuance and persistence should be atomic with uniqueness protection.
Health-log insertion should be atomic; a failed health-log write must not create a partial record.
Reward creation associated with a verified activity should be consistent with the activity that triggered it; exact reward transaction behavior is finalized in the service/API design.
24. Concurrency Considerations
Two coordinators may attempt to verify the same tree; backend state transition checks and transactions must prevent contradictory final states.
Two verification requests must not generate two permanent Tree IDs for the same tree.
Database uniqueness constraints remain the final defense against duplicate Tree IDs.
Health-log creation is append-oriented and normally does not conflict with previous logs.
25. Data Lifecycle
Registration   ↓Tree created: Pending   ↓Verification events   ↓Verified   ↓Tree ID assigned   ↓QR/Public Profile   ↓HealthLogs accumulate   ↓Dashboard aggregates
Tree record persists through the lifecycle.
Verification records are historical.
Health logs accumulate over time.
Tree ID remains stable.
Deletion/archival policy is not frozen for V1 and must not be invented.
26. Migration and Seed Strategy
Use version-controlled database migrations.
First migration enables PostGIS.
Subsequent migrations create core tables and constraints in dependency order.
Seed suitability rules with the approved 10-species data.
Development/test seed data must be clearly distinguishable from real pilot records.
Do not commit production secrets or credentials in migration/seed files.
Recommended migration dependency order:1. PostGIS extension2. users3. suitability_rules4. trees5. verifications6. health_logs7. rewards8. indexes / additional constraints / seed data
27. Backup and Recovery — V1
Use the selected managed PostgreSQL provider's backup capability where available.
Database backup credentials/configuration remain deployment secrets.
Before pilot use, verify that the deployed database can be restored according to the selected hosting provider's supported process.
Disaster-recovery RPO/RTO targets are not defined for the semester pilot and should not be invented.
28. Database Security
Database credentials must be stored in server-side environment variables/secrets.
Frontend must never connect directly to PostgreSQL.
Database network access should be restricted to the backend/deployment environment where supported.
Least-privilege database credentials should be used where feasible.
Never expose password hashes through APIs.
Public profile queries must select only privacy-safe fields.

31. Open Database Decisions — Must Not Be Guessed
Exact internal primary-key strategy: UUID vs BIGINT.
Exact migration tool.
Exact ORM/query approach.
Exact enum implementation: PostgreSQL ENUM vs constrained VARCHAR.
Exact Tree ID format/prefix and sequence/random generation policy.
Exact health-status values.
Exact photo-storage provider and media retention policy.
Exact user contact fields beyond the authentication identity.
Exact cascade/soft-delete/archival policy.
Exact public-location precision rule.
Exact reward point values and badge schema if badges require a separate table.
Whether a separate species master table is required instead of a species field/rule table; if introduced, it must preserve the 10 approved rules and avoid unnecessary schema complexity.
A coding model must not silently invent these decisions. Before implementation, resolve them in the project decision log/API/Database implementation plan.
32. Recommended Exact Implementation Order
Create database and verify PostgreSQL connectivity.
Enable PostGIS.
Create users table and role constraint.
Create suitability_rules table and seed the 10 species.
Create trees table with PostGIS geometry, status, contributor FK, and Tree ID uniqueness.
Create verification table and foreign keys.
Create health_logs table and foreign keys.
Create rewards table.
Create relational and spatial indexes.
Run migration validation.
Run database unit/integration tests.
Only after the database passes tests should dependent backend modules be built against it.

35. Final Database Principle
The EcoRevive database is the source of truth for persistent identity, spatial plantation records, verification history, monitoring history, and reward events. The design must favor integrity and auditability over unnecessary complexity. PostGIS is a first-class requirement, not an optional add-on, and Tree ID uniqueness must be enforced at the database boundary.
